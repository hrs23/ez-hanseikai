# Design

How the app is built and why. The principles are in the [README](../README.md#key-principles). The files are in [session-format.md](session-format.md), the messages in [protocol.md](protocol.md), the local API in [llms.txt](llms.txt) and every tested case in [test-cases.md](test-cases.md).

## Shape

- A Windows app, the same for everyone: a Tauri shell with a Rust core that captures, encodes, syncs and keeps the logs, and a web UI in one window. The UI reaches the core through one `call` command that dispatches into the list of operations in `ops.rs`, which the local API uses too. One shared `Core` holds the state; background threads run the capture and encoder supervisor, the analysis worker, thumbnails and cleanup, and async tasks run the network, the Watch Party repeat and the relay check.
- One window: a left sidebar that is the room and a main area for what is chosen there, with a native menu that mirrors the commands. The room part of the sidebar and the player's shared region are shared; the bottom of the sidebar, Settings and the player's own controls are personal. A destructive action says whether it affects this PC only or everyone.
- Capture and Settings stay apart, as in Discord, OBS and Zoom: what is touched every evening (the screen, the app sound, the microphone) sits in small menus on the Screen and Microphone buttons, and what is set once is in Settings. One page holding both would put the meters next to rarely used settings and take the user away from the player to change the microphone.
- Every English string is looked up in one dictionary (`ui/i18n.js`), also the fixed messages from the core; the core sends codes for notices that carry values. The native menu, message boxes and notifications have their own table in `shell.rs`. A test keeps the dictionary and the code in step both ways: every phrase used has Japanese and every entry is used.
- Each member has one of eight colours, the same on every PC: the one they chose, else one taken from a hash of their ID with the next free colour when it clashes. It marks their face, notes and drawings.
- A member's avatar shows when they speak, wherever it is drawn: a ring in their colour, with a glow and a light pulse from 24px up. Avatars in dense lists (members table, notes, watcher pills, volume popup, diagnostics) are drawn still and never light.
- One app runs per data folder (a lock file); a second start brings the running window to the front. Closing the window quits, asking only while files arrive or an export runs.

## Data flow

1. The screen is captured with Windows Graphics Capture and the app's sound per process; the picture is scaled to the quality's width and converted to NV12 on the GPU (on the CPU when the GPU cannot).
2. One ffmpeg process per person encodes it once into two fragmented MP4 series that it sends to the app over localhost: `v` (picture and app sound) and `m` (voice, from the microphone).
3. The app cuts the fragments (one second each) into segments of four, and also at once on Start and Stop, so a recording starts and ends on a fragment. Live and recording are the same segments: a recording is the list of segments logged for it.
4. Each recorder appends the size and SHA-256 of every init and segment to its own append-only room log. Notes, marks and every other event go into the same log.
5. Members pull each other's logs and files over iroh. The player and Live read the parts through the app's `ezh://` scheme and play them with Media Source Extensions, so a seek is a fetch of one segment however far it goes.

The order of importance on the wire is logs, voice, live picture, then history. A live stream that falls two segments behind ends and restarts at the newest; history waits while live is flowing and always keeps a quarter of the upload limit.

## Reasons

- Each person writes only their own files and everyone keeps everyone's, so the room survives anyone leaving and logs merge without conflicts. The logs are the source of truth; everything shown is computed from them.
- Segments are four seconds because that keeps a live joiner close to now and the file count low (about 900 per hour per series).
- One codec per room: the best that every member can play (AV1, then HEVC, then H.264), a keyframe every second, no B-frames and no separate full-quality copy.
- There is no host or leader: any member can start or stop a recording, rename the room, remove a member or run an extension, and the newest record wins.
- Clocks differ between PCs. Every PC asks a public time server for the time, peers measure each other's clocks, and playback lines up a recording from these. The newest-wins records are compared on each log's clock offset, and a rename is stamped after every name already known so a fast clock cannot undo it.
- No picture crosses a relay, live or recorded: voice, notes and logs do, and the picture follows once the path is direct.
- After a crash each unfinished own segment is cut back to its last whole fragment, finished and logged, and an open recording gets its end. A Stop is a record in the log, so a member that missed the message ends the recording when it finds the record in any log.
- Every write goes to the open room, and only once this PC is a member of it (`Core::joined_room`). Every deliberate stop (exit, reset, installing an update) ends this PC's part first and cancels an export (`data::release`).
- Files go only when asked (Delete, Clean up, Reset); the app removes on its own only temporary files. Clean up classifies every file in the data folder by one table of patterns (`RULES` in `cleanup.rs`): files the app made in a known shape that no room log refers to, older versions' files and temporary files, unchanged for a day, plus whole folders of older versions of the app listed by exact name in `LEGACY`, only when every entry in them is a name the app made and never the running app's own folders. The review lists them by group with sizes and moves only what is ticked. It moves them to the Recycle Bin through the Windows shell, refusing any that would be deleted for good instead, deletes only the temporary ones, checks each again just before, and refuses while a recording, an export or an analysis runs. Unknown names, logs, keys, settings and `rooms.json` are never touched.
- An event is one kind of record for notes, marks, drawings, game plan cards and extension results. The player shows each by its shape (a moment, a range with text, a chapter), never by extension.
- An extension is its own process (`ez-hanseikai.exe --plugin`, idle priority, ended with the app): a job goes in as JSON on stdin and the result comes out as JSON lines (the job fields and the progress, output and error lines are defined in `src-tauri/src/plugins/mod.rs`), so a crash or a hang cannot harm the app, and the app knows nothing of its internals. An extension lists the settings it has (`options` in its manifest: a name and what the empty choice means); the app shows them the same way, stores their values per room with the on or off record and knows nothing else about them. Extensions are chosen per room, and one runner per extension does the work, so a recording is analysed once. A built-in extension always runs the version this app ships, whatever version the room's record names, and the Analysis rows take their reason from the same checks the runner makes before it starts a job. Only a recording that ended within the last hour, or one already started or asked for, is analysed on its own; an older one waits for Analyze, which is a retry record in the log like Retry. A view extension has no process or job and only names a view that the player draws from the video it already plays: with Apex minimap on in the room, the All view gets one more tile, in the grid's free cell or added at the end, with the top-left corner of the heard member's picture, a square whose size and offset follow the frame height (`minimapRect` in `ui/layout.js`). Apex match detection reads one 64x36 picture per keyframe (one a second), cut to the 16:9 middle so it holds at any resolution: a match ends at the first gray results screen with a red banner across, and starts at the drop, right after the second of the two blue APEX cards between the lobby and the drop ship (the first comes before legend select); a match without a plausible start runs from the previous end. Excitement detection reads each member's voice as half-second loudness levels: their usual voice is the median of the windows at least 10 dB over the quietest tenth, and a mark goes where the voice stays 12 dB over that for a second, at most one every 30 seconds.
- Watch Party follows the recording each member has open; opening another recording from the list leaves the party for that member (the old recording shows a Back button that returns and joins again). A debrief belongs to its recording: the recordings list and Recordings in Settings show it as a count on that recording, its size is counted with the recording and it is deleted with it. Each person plays their own copy, and every tile waits for the others after Play or a seek so all start together.
- The one global shortcut, mark this moment (Ctrl+Alt+M by default; the old Ctrl+Alt+K moves to it), is armed only while recording, so it never takes a key from a game otherwise, and a notification says what happened when the window is not in front. In the window, M turns the microphone and V the screen picture on and off, only while recording, with no text field focused and not while a recording plays (there M is Mute); they press the dock buttons, so V asks before it stops sending, and the buttons' tooltips show the keys.
- A member coming online in the open room while the window is not in front gets one small notice in the screen corner and the join chime, both from the core: Windows holds back its own notifications during full-screen games, so the notice is a window made unfocusable from the start and never takes keys from the game. Joins in the first seconds after start or opening the room are not news.
- A debrief is a voice-only recording made while watching another recording and linked to it by `of`. There is no debrief player: the exported folder, the debrief video (`debrief.rs`: spans from the `party` records, one ffmpeg job per few spans, then the voices mixed, then both joined with no re-encode) and the API are how it is read.

Player diagnostics: when the picture freezes, the app log has `player:` lines (at most 20 a minute, more are counted as skipped). `seek` shows a tile that was steered by a jump of more than 0.4 s while playing (drift in seconds, buffered ahead, ready state); `waiting`, `stalled` and `seeking` show the tile's time, the seconds buffered ahead and the ready state: a short `ahead` means the feed is late. `dropped` lists tiles that dropped frames in the last second, with the tile count and whether the minimap is on, and `longtask` or `long-animation-frame` means the page was blocked that many milliseconds: both point at decoding or drawing, not the feed. `decode` is once per recording and codec; `powerEfficient=false` means software decoding.
