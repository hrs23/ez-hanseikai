# Design

What the app does and how, as built. What is decided but not built is under [Planned](#planned).

## Shape

- A Windows app, the same for everyone. Tauri: a Rust core that captures, encodes and syncs; a web UI. The window keeps the standard Windows caption buttons and, on Windows 11, its title bar, border and text take the sidebar's colours (`DwmSetWindowAttribute`; ignored on older Windows). Closing the window quits the app, asking first only while recording, files arrive or an export runs; minimizing keeps it in the taskbar. One app runs per data folder: a second start brings the running window to the front, and an app on the same folder from another build says so and exits (a lock file `app.lock` in the data folder; one left behind by a kill or crash is only logged, and the app resumes on its own).
- One window: a left sidebar that is the room, and a main area for what is chosen there. No tabs and no top bar. A native menu bar (File, Room, Recording, View, Help) mirrors the commands. Each action and piece of information has one place, with no explanatory text; status sits next to what it affects. Logs stay in the diagnostics window.
- The sidebar, top to bottom: the room's name with a ▾ (long names end in an ellipsis; the menu holds Room settings…, Copy invite code (and Cancel invite while one is open), Switch room and Leave room…) and, under it, the members' faces (green online, red recording, faded offline) and, while the local API is on, its badge; four items, Live, Game plan, Members and Plugins (Jobs are a second view inside Plugins), each marking the page open in the main area, with a count for join requests on Members and for failed jobs on Plugins (and on its Jobs switch); the record box (the Start recording button with ▾ for Record debrief, and under it Standby and how many are online); the Recordings header, which opens the full recordings view, above the list of every recording, newest first, scrolling by itself; a warning when free space runs low; and at the bottom the Screen and Microphone buttons and the own row (name, short ID, a Direct or Via relay badge that opens where data goes, and the settings gear). Room-wide things are above, personal ones at the bottom. The sidebar's width is dragged at its right edge (double-click resets it, the arrow keys move it), kept between 220 and 420 px and remembered on this PC; nothing in it ever scrolls sideways, and long text ends in an ellipsis. Ctrl+1 to Ctrl+4 open Live, Game plan, Members and Plugins; Ctrl+B hides the sidebar; Ctrl+, opens Settings.
- Shared and personal stay apart: the room part of the sidebar and the player's outlined region are shared; the bottom of the sidebar, Settings and the player's own controls are personal. Destructive actions say whether they affect only this PC or everyone. Confirmations are in-app dialogs; file pickers and the few native message boxes come from the Windows dialogs.
- Capture and Settings stay apart, as in Discord, OBS and Zoom: what is touched every evening (the screen, the app whose sound is recorded, the microphone, their meters and volumes) sits in small menus on the Screen and Microphone buttons; what is set once (name, language, ID key, quality and upload limit, shortcuts, recording sounds, recordings on this PC, the local API, updates) is in the Settings window. One page holding both would put the meters next to rarely used settings and take the user away from the player to change the microphone.
- Everyday review features live in the app: recording, sharing, rooms, playback, notes, drawing, Watch Party, export and showing events. Game-specific analysis lives in plugins. The UI says "app" for capture sources and their sound; game terms such as matches come from plugins as tags and chapters.
- Nothing goes to a cloud. Everyone is equal: no host and no leader for recording or playback.
- English and Japanese, following the Windows display language until one is chosen in the settings. The UI looks up each English string in one dictionary (`ui/i18n.js`), so fixed messages from the core are translated the same way; the core sends codes for notices that carry values. The native menu, message boxes and notifications have their own small table.
- One icon set (Lucide, inlined in `ui/icons.js`) and one set of design tokens in `ui/style.css`.
- Each member has a colour, the same on every PC: members (and removed members) sorted by ID take the palette in order. It marks their avatar, notes and drawings.

## Identity

One key per person, made on first start; its public half is the person's ID everywhere. The name can change; the ID cannot. Moving to a new PC means exporting and importing the key (File menu).

## Rooms

- Without a room the window shows the start screen: the name, the recent rooms with Enter (the most recently used first; ⋯ offers Leave room…), Join with a code and Create room. While a join waits for approval it shows that, with Cancel.
- One room is open at a time. Switch room (in the room menu) returns to the start screen and keeps the room and its data on this PC, and Enter there goes back in; Leave room… asks first (saying the recording stops when one is running) and removes the room, its data and the personal game plan from this PC, but not while a recording of that room is exported or imported. Other members keep theirs.
- The room opens on Live. The main area shows the page chosen in the sidebar, each with a header (its title, the member count on Members, AI). Members is a table of everyone with their ID, one short status, direct or relay connection, round trip and version (another version in the warning colour), with join requests and an open invite above it. The status is exactly one of Not sharing a screen, Standby (sharing, not recording), Recording, Receiving n% (a recording from the last 12 hours that the member holds only part of) or Offline with the last time they were seen. Recordings is described under Recordings on this PC. Room settings (a dialog from the room menu) holds the room name. A member's detail pane shows the connection (the relay server's name when relayed, round trip, bytes sent and received, clock offset, version), what this PC is receiving from them, their check results and Remove from room. Checks run on their own when the pane opens and again on request. Game plan is described under Events; Plugins and Jobs are described under Plugins.
- Invite codes work once, only while the inviter's app runs, and can be cancelled. Creating a room copies an invite code. Any member can invite.
- Any member can rename the room (room menu > Room settings…): a `room_name` record in their log; the newest (by each log's clock offset) wins everywhere; a rename is stamped after every name already known, so a member whose clock runs ahead cannot undo it. A plugin's settings change is stamped the same way.
- A room is meant to be kept and reused, so its history builds up; a new room starts with its own empty history.
- Joining needs approval: someone using a code asks to join, every member online sees a row "<name> wants to join" with Approve and Decline in the Members list (and a Windows notification while the window is minimized), and nothing of the room is sent until a member approves. The request ends with the invite.
- Any member can remove a member for the whole room: the removal is a record in the remover's log, so it reaches everyone; everyone stops sending to them from then on and refuses their connections, and everyone sees who removed whom. What they already received stays with them. A later approval lets them back in.
- Leaving a room deletes it from this PC only.

## Live and recording

- The Screen button at the bottom left (like Discord's) shows what is sent: Screen off (dashed), the window or display and Sending live (green), or Recording · live (red). Clicking it when off opens the picker; clicking it when on turns the screen off. Its arrow opens the picker: windows, displays with their size, Turn screen off, and the app whose sound is recorded with its meter, volume and mute. Every start begins with no source and the microphone muted, so nothing is sent until the player chooses; the choice is not kept for the next start. A capture problem shows on the button. A shared window that closes stops the capture and shows as lost; the app never moves to another window of the same program (only the same window may change its title).
- The Microphone button mutes and unmutes and shows the same states as Screen: muted (dashed), on (green) or recording (red), with a level meter inside it; its arrow chooses the microphone and shows its meter, volume and mute. The microphone is its own track and muted at every start. The volumes of app sound and microphone are kept on this PC. App sound comes from per-process capture.
- Inside a room everyone's picture and sound stream all the time while their screen is on; Live (the first sidebar item, where the room opens) shows a tile for everyone online, before any recording exists, while nothing records and while a recording runs: their picture a few seconds behind while they share a screen, Screen off otherwise, and the own tile offers Choose screen while the screen is off. Turning the screen off stops only the live picture: recordings already made are sent as before. The upload limit (Settings > Capture) caps the upload.
- The unit is a recording, one per room: anyone's Start recording (the sidebar button or Recording menu, after a confirmation) starts it for every member and anyone's Stop recording (also confirmed) ends it, with no shortcut key. Every member sees "Aki started recording" or "Ren stopped recording" in the app with a short sound (Settings > General turns the sound off); there are no Windows notifications. Every member sees the same list. Nothing is kept while nobody records. A member with the screen off records only their voice; a member who joins mid-recording records from then on; an absent member is an empty tile. While recording, the Stop recording button shows a red dot and the elapsed time, and the first row of the recordings list shows a red dot, Recording and the current match (or who started it) and opens the player at the latest moment; the record box shows Standby and how many are online while nothing records, and opens Live. (Records and code call a session a set.)
- Mark this moment (Recording menu or a global hotkey, Ctrl+Alt+M by default and changeable in Settings) logs a `mark` event at the current time of the recording. The hotkey is registered with Windows only while recording and never touches the game.
- The capture is scaled down to the quality's width and converted to NV12 (BT.709) on the GPU before it reaches ffmpeg, or on the CPU when the GPU cannot. One ffmpeg process per person encodes it once into two fragmented MP4 series that it sends to the app over localhost: `v` (picture and app sound) and `m` (voice). Each fragment is one second. The app cuts them into segments of 4 fragments, and also at once on Record and Stop, so a set starts and ends on a fragment. Four seconds keeps a live joiner close to now and keeps the file count low (about 900 per hour per series). Live and recording are the same segments: a recording is the list of segments logged for the set.
- A capture is one encoder run; a restart (new size, codec or quality, or a crash) starts a new capture, so a set can have several parts per member. A new size or quality waits until no set is recording. An encoder that exits, or gives no output for 10 s while frames keep coming or a frame write does not return, is stopped and restarted into the same set; after three failures in a row without a minute of output it is skipped for ten minutes for the next working encoder (another backend of the same codec first), down to libx264. The old ffmpeg is stopped before the next one starts. Which encoders work is probed once, each probe with a time limit, and kept until ffmpeg or the GPU driver changes. Until the new encoder gives output, the preview and the own row show the problem and the own tile does not show recording. Screen capture never waits on ffmpeg (a feeder thread per capture writes only the newest frame), and sound writes to it time out.
- Quality presets, each with its width at 30 fps: Light 960, Standard 1280 (the default), High 1920. The height follows the source's shape and nothing is scaled up. The bit rate is 0.2 bits per pixel per frame of the preset's 16:9 size for H.264, times 0.7 for HEVC and 0.55 for AV1 (Standard: 5.5 Mbit/s H.264, 3.0 Mbit/s AV1). Capture shows the resolution, frame rate, bit rate and codec in use.
- Meters show the level after the volume, in dB from -60 to 0 like OBS: green, yellow from -20 dB, red from -9 dB, the highest peak held for 1.5 s, and a clip mark for 3 s after a full-scale sample.
- Codec: AV1, then HEVC, then H.264, the best one that every member can play. A keyframe every second, no B-frames. There is no separate full-quality copy.

## Data

- Each person writes their own append-only files: their recordings and their log. Settings live in `settings.json` on each PC. The logs are the source of truth; a torn last record is dropped on start.
- One log per person per room, `rooms/<room>/logs/<member-id>.bin`. Members receive only that room's logs, and everyone keeps every member's log of the room, so the room survives anyone leaving. A person whose own log of a room is empty (a new PC with an imported key, or a deleted data folder) first gets it back from a member, then writes; until every member has said how much of it they hold (or one connection attempt has passed) and none holds more, new records wait in `pending.bin`.
- Each recording has one folder, written there from the first byte on every PC, by its recorder and by everyone who receives it: `rooms/<room>/recordings/<recording>/<member-id>/<capture start ms>/{v,m}/` holds `init.mp4` and `000001.m4s`, `000002.m4s`, and so on, each written as `.part` and renamed when complete, and nothing else; the recorder opens a segment only in a folder that already holds its capture's `init.mp4`. Segments that belong to no recording (the live picture while nobody records) go to `rooms/<room>/standby/<member-id>/<capture start ms>/{v,m}/`, which keeps only the newest few of each series and is emptied at every start. Folders of older versions (`rooms/<room>/<member-id>/`, `sets/`, `live/`) and JSON files in recording folders are kept and not read.
- The owner logs `cap` (capture start, settings, size and SHA-256 of each init it has) when the capture's first segment of a set opens, and again when a later one opens after another init came in (a capture's `cap` records are merged), and `seg` (capture, series, number, set, start, duration, size and SHA-256) for segments in a set only; live-only segments are never logged. A member's part of a set is its `seg` records for that set. The set's default layout is the last `layout` record for it.
- After a crash, each own `.part` in a recording folder without a `seg` record is cut back to its last whole fragment, finished and logged, as is an own segment that was finished but not logged, and an open set gets its `rec_end`; if the set is still recording elsewhere, the member joins it again with a new `rec`. A Stop marks its `rec_end` (`stop`), so a member that missed the message ends the set when it finds that record in any log.
- Log record kinds include `rec`, `rec_end`, `cap`, `seg`, `file_bad`, `event`, `event_edit`, `event_del`, `event_restore`, `set_del`, `remove`, `admit`, `room_name`, `offset`, `layout`, `plugin`, `job` and `party`. Unknown kinds are kept and ignored. Edits and deletions are new records.
- The app works from an empty data folder, and recreates its files if the folder is deleted while it runs; without `key.bin` it makes a new identity at the next start and says so.

## Sharing

- Peers connect directly with iroh, through a relay when they must. Connections are encrypted and accepted only from room members. Address lookup publishes only the relay URL.
- One connection per pair of members, used both ways: the member with the lower ID dials, and someone joining dials the member whose invite they use. A new connection from a peer that still has a working one (it answers a ping within 3 s) is refused, so two connections never close each other. A failed dial, or a connection that ends within 10 s, doubles the wait before the next dial, from 2 s up to 30 s, with a quarter of random spread so peers do not dial in step. While a join waits for approval, the joiner asks again every log sync on the same connection.
- On connecting, members pull every member's log from any peer that has it, so late or offline members learn every recording (the list), though not its videos.
- Media moves with one request, follow: from a segment and byte, the sender streams segments in order, waits on the open one and goes on into new ones. Live follows each member's current segment, and the owner's answer says which recording it belongs to, so it is written straight into that recording's folder; a live stream ends where a recording starts or stops and the next one continues in the right folder. Missing segments come the same way from the owner or any member that holds them, resuming where they stopped. Only the recording in progress is received on its own (live sharing and gap repair), and a recording this PC already holds some of keeps being completed. A finished recording that is not on this PC, including one made while this PC was offline or imported by someone else, is fetched only when its Download button is pressed.
- Order of importance: logs, voice, live picture, then history (voice before picture). The speed limit caps the upload; history always keeps a quarter of it, so live streams cannot stop it.
- The player and Live read media through the app's `ezh://` scheme, which joins the init and segments into one growing file with byte ranges.

## Verification

Each recorder logs the size and SHA-256 of every init and set segment. A fetched copy is checked once, when it arrives; one that does not match is logged as `file_bad` and deleted, and a member that sent all of it is not asked for it again until the next start. Live copies come straight from the recorder and are kept as they arrive. A file counts as here when it has its logged size, and members tell each other, per set, member and series, how many segments they hold in order, so the set list shows whether everyone has everything or what is missing.

## Time

Peers measure clock offsets continuously and log them. Playback lines up everyone in a set from the recording start times and the offsets, with a manual nudge.

## Player and Watch Party

- One player shows the live tiles (Live), the recording in progress and past recordings. Its header has the title, a chip (Recording with the timer, Recorded, or Debrief), the length and matches, the Watch Party control and the side panel button. Below it the shared region holds the views and drawing tools, the tiles and, along the bottom like YouTube's, the chapters, event marks, seekbar and one bar of controls: play, back, forward, volume, time, the current match (opening a list of matches), Latest or Jump to latest, Note, volume per member, subtitles, speed, layout and full screen. The region is outlined in the accent colour while Watch Party is on.
- At the latest moment of a recording in progress the seekbar is red and the bar shows ● Latest; further back the header says how far behind the latest and the button reads Jump to latest −2:14. The end of the recording in progress grows with a dashed red tail.
- The side panel has three tabs: Review lists the matches, each with its notes, marks and match end and a Watch button, with A/D and Q/E as hints, then the debriefs of this recording and Write to the game plan; Notes lists every event with the filter; Talk is the transcript.
- Each person plays their own copy. Views: all players, or one player's picture and sound (keys 0 and 1 to 6).
- Layouts: a two-tier picker chooses the number of places (1 to 6, never fewer than the players present; the rest stay free) and then auto grid, one large with the others beside or below, or a row. Dragging a name label swaps two players. The recorder's layout is the set's default; each viewer can rearrange.
- Click toggles play, double-click shows one player, F is full screen. Shortcuts (View > Keyboard shortcuts): Space/K, arrows and J/L to skip (Shift and Ctrl+arrows for longer), < > for speed up to 3x, Shift+P/N for the previous and next recording, Q/E for notes, A/D for a minute before the previous or next match end (other events and chapters when there are no matches), C for a quick note, X to clear drawings, Ctrl+Z to undo the last seek or deletion.
- Watch Party: everyone who joins sees the same thing, with no leader. Outside it the header shows how many watch with a Join button; inside, the viewers' avatars and Leave. One shared state holds the set, playback (playing, position as wall time, speed), view, layout and tile order; it is ordered by a Lamport counter, then time, then sender, the newest wins, and it is repeated every few seconds, so anyone who joins catches up. Turning it on joins what the others are watching and never moves them: a state from turning on has counter 0 and the negative turn-on time, so any action and any earlier turn-on wins over it. Each message also carries how many records of each member's log the sender holds and how much of the set it has. Those counts only grow; everyone shows only events below them, fetches what it lacks at once, and shows "Catching up with Ren" or "Ren receiving 72%" to all until it has it, or "Ren incomplete at 72%" when no member online has more. Choosing a set switches everyone; a member without the files fetches that set first and shows its tiles as receiving where it has no picture yet. When someone else plays, pauses or seeks, their avatar marks the place on the seekbar and a line says who did what; Ctrl+Z undoes the last seek. Volume stays personal; outside Watch Party the layout is each viewer's own.
- Each tile plays its picture and app sound and, as a separate audio stream on the same clock, its voice. Everyone's voice is heard in every view; app sound comes from the chosen player, and in All players from the viewer's own player (the first one when the viewer did not record). The player starts with sound on at full volume, whatever the microphone muting at capture start, and the page plays sound without needing a click first.
- Volume is personal: one volume and mute for the player, and app sound and voice volume and mute per member (from the control bar or a player's name label), kept on this PC.
- Hovering the seekbar shows the frame of the shown player at that time (a hidden copy of the player seeks there), and the chapter.
- Sync status sits on what it concerns (downloads of the video tools and of plugin models show the same percent, speed and time left above the page): a recording row shows this PC's receiving with percent, speed and time left (or where it stopped), the running analysis and an export; a tile shows how much of that member's file is here; while Watch Party is on, the stage shows who is catching up or still receiving.

## Debriefs

- A recording started while this PC is in Watch Party watching a recording is a debrief: the main button reads Record debrief with the microphone, every member records only the voice series (`m`), and the header says Debrief with the time (the length of the watched recording gives way when the header is too narrow) and the first row says Voice only. The record button is split: its ▾ menu offers Start recording and Record debrief, so a debrief can also be recorded outside Watch Party (`start_recording` takes `debrief`; without it the app decides from Watch Party as before). Both ask first, and the debrief question says that only the voice and the viewing flow are recorded. The `rec` record and the start message carry `voice`, so members who join later record the same way. Nothing else marks a review: the list shows the Debrief badge for a recording whose parts are voice only and that has `party` records.
- While any recording runs, each member logs the Watch Party actions they make as `party` records (the set being recorded, the time and the shared state), and the starter logs the state at the start. These are the only traces Watch Party leaves.
- Opening a debrief replays it: the debrief's voices play on its own clock, and the shared state at each moment (the recording watched, its position, play or pause, view and layout, and switches to other recordings) drives the player, so drawings shown when paused appear too. The seekbar seeks the review; coloured bands under it show which recording was watched when; Open this moment leaves the replay at that place. The side panel has Talk, Notes and Shown, the list of what was opened, played, paused and moved. In Watch Party everyone replays together.

## Events

Notes, markers, drawings, board cards and plugin results are one kind of record, an event: who made it (the person whose log holds it, or a plugin name and version), its kind, an optional target (a moment, a range, a file or the whole set) and its content (text or numbers), with tags (people write `#tag` in a note; plugins tag their own). Only people's events can be edited or deleted, and a deletion can be undone. A moment belongs to the room, so every set covering it shows the event; clicking one seeks everyone in Watch Party. The app makes notes, drawings and board cards; other kinds come from plugins.

The Player shows every event by its shape, never by plugin:

- A moment: a mark on the seekbar, a row in the event list, and, with text, a line over the video for 8 seconds.
- A range on one member's file with text (such as speech): a subtitle on that member's tile (CC switches it) and a line in the Conversation list, which follows playback and seeks on click.
- Any other range: a chapter above the seekbar and a row in the list.
- Moments a plugin tags `match` are match ends: the chapters between them are "Match 1, 2, …" (the open one only while recording), and the current match shows beside the clock.

The filter above the list searches text, names and kinds, and `#tag` (or clicking a tag) lists that tag's events, in this recording or, with its scope, in all recordings of the room. A quick note (C or the note button) pauses, opens a box over the video at that time (Tab: without a time, or completes a tag), and Enter adds it and resumes; while it is open others in Watch Party see "<name> is typing". Right-clicking the video copies a link to the moment and view (`ezh://moment/<set>/<seconds>/<member>`); links in notes and on the board open it in the app.

The game plan (the Game plan item) is a Markdown page, either the room's or the person's own; a switch at its top chooses between Room and Personal. The room's is the newest `board` event: `#` is the title, the first paragraph the goal, each `##` a card of the same width in three columns, and a card holding moment links spans the width; links to moments open them. A new room, or one whose page was cleared, shows a starter page. The personal page has the same layout; it is kept only on this PC, per room, in the window's local storage (never in a log, so never sent; leaving the room, or Help > Reset app without keeping rooms, removes it), and the header says so. While editing, the Room and Personal switch stays visible but locked. The Markdown is rendered as DOM nodes from text only, never as HTML: headings, bold, italic, strikethrough, ==highlight==, inline code and fenced code, bullet, numbered, nested and task lists, quotes, rules, tables, links and `#tags`. Links open only when they are `https:` or `http:` (in the default browser, through the app, with characters outside ASCII percent-encoded; a link whose text does not show its host, or whose host has characters outside ASCII, asks first, naming the host) or a `ezh://moment/…` link (in the player); anything else, images and raw HTML stay as plain text. Ticking a task box rewrites that line and saves the page (an event for the room's page). The page is laid out at a fixed width and zoomed to fit, with − and + and full screen (F); Edit shows the Markdown beside a live preview, and Ctrl+Enter saves.

## Drawing

Part of the app. Drag on a paused frame to draw: pen, arrow and a laser that fades (the laser works while playing too), X clears, one colour per person. Points are kept relative to the drawn player's picture, so strokes stay in place whatever the layout. In Watch Party strokes go to everyone as they are drawn; finished pen and arrow strokes are kept as `drawing` events (player, tool, points, moment) and show whenever playback is paused at that moment. Clearing hides the strokes at that moment for everyone until playback moves on.

## Plugins

- Analysis only: a plugin reads recordings (picture and sound) and set information and writes events, plus an optional tag dictionary (tag to display name). It has no UI; the app shows every plugin's events the same way. It never touches the game.
- Self-contained: its own program, depending on no other plugin and turned on or off on its own. The app knows nothing about its internals. Each plugin runs as a separate process of the app (`ez-hanseikai.exe --plugin`, idle priority; every child process of the app ends with it): the job comes as JSON on stdin (plugin, settings, set and file information, duration, picture, app sound and voice as file parts plus a stream, the ffmpeg path, its own folder `plugins/<id>` and a scratch folder), and it answers with JSON lines on stdout, `{"progress": 0.4}` and finally `{"output": {"events": [...], "tags": {...}}}` or `{"error": "..."}`. Event times are seconds from the start of the file (`at_s`, or `from_s` and `to_s`); the app turns them into wall times.
- A plugin declares an id, a name, a version, whether it may run while recording, its settings as lists of choices (the first is the default), and the files it needs for given settings (URL, SHA-256, size). Those are downloaded into `plugins/<id>` only when a member asks; until then that PC runs none of its jobs.
- Chosen per room with their settings, so everyone gets results from the same plugin versions and settings: a `plugin` record holds the plugin, on or off, the version of whoever set it, and the settings; the newest wins. Only members with that version run its jobs. Each person only chooses which results to show.
- A plugin whose result is about the whole set rather than one member (it declares so) runs once per set, on the file of the member with the most picture segments (the lowest ID on a tie), which every member derives the same from the logs; only that job's results are shown. Other plugins run on every file.
- Members share the work: a job is one plugin version and settings on one file (its key is `<plugin>@<version>/<settings hash>/<set>/<owner>`; a member's file in a set is read capture by capture, each as its `init.mp4` and segments in order, so a restarted capture adds no job; the plugin runs once per capture and the results are joined). Any member that holds the whole file, processes the plugin and is idle (and is the plugin's chosen runner, if one is chosen) claims it with a `job` record in its log (`state` `claim`, then `done`, `fail` or `stop`, each with `job`, `run`, `plugin`, `version` and `file`; `retry` clears its own failure; a claim waits two log syncs and, if a connected member claimed the job earlier or another member already finished it, gives way with `yield`), runs it and writes the events and then `done` there. Its own unfinished claim goes first, then its own recordings, then the newest sets. A claim by a member who is not connected can be taken by another member. Of several `done` runs of a job only one is shown (the lowest member ID), and events of a run without `done` are never shown, so an interrupted run leaves nothing behind and reruns from scratch.
- Only results of jobs that match the room's current plugin choice are shown; changing a setting or the version starts new jobs.
- Jobs run one at a time per PC on finished files, stop when recording starts (unless the plugin may run while recording) and rerun later, and skip files already done. A run stopped on purpose (recording, a changed choice, exit or an update) logs `stop`. A job this PC claimed twice without `done`, `fail` or `stop` is logged as failed instead of being claimed a third time: one interruption can have another cause, two on the same job point to the job. A claim this PC holds without `done`, `fail` or `stop` is logged as `stop` as soon as this PC no longer runs that plugin (another runner chosen, Process on this PC off, another version), so another member can take it.
- Each plugin has a room-wide "Who runs it" choice: Auto (the default) or one member. It is a `runner` field of the plugin's record, not of its settings, so it changes no job's key. With Auto, any member whose "Process on this PC" is on takes the next job when idle and the claim is logged; when only one member processes the plugin, that member runs everything. A chosen member alone claims the plugin's jobs, and they wait while that member is offline; a chosen member who is no longer in the room counts as Auto. The jobs list shows who ran or runs each job: the claimer, else the chosen member, else the only member who processes, else Auto.
- Each plugin has a "Process on this PC" switch (on by default; a PC setting, not the room's), so a weak PC can leave a plugin's jobs to the others. Each member logs a `worker` record per plugin with that switch and whether the plugin's files are on that PC, so everyone sees who processes it.
- The downloader reports the bytes it has written (read from the partial file) so that the plugin page shows percent, speed and time left.
- A plugin's output lines are read up to 16 MB each, far more than any result; a longer line fails the job.
- Official plugins only, kept in this repository and bundled.
- The Plugins page reads like an extension list, with Plugins and Jobs as a switch at its top: Enabled in this room on top, Available plugins below, each row with a one-line summary and a small sample (chapters on a seek bar, a subtitle). Turning a plugin on or off, or changing its settings, asks first and says it applies to everyone in the room. An enabled plugin opens to its settings (an Everyone badge marks them as the room's), who processes it (the Who runs it choice, then every member with Off, Needs download, Ready or Processing, and the switch for this PC), the progress in finished recordings, and this PC's download with percent, speed and time left. The Jobs view lists every job of the current choice (plugin and model, recording, whose voice or the whole recording, state with progress, the PC that runs or ran it, a failure's message) with All, Active and Failed; a job's menu runs it next on this PC (when this PC may run it), retries a failure, stops a running one, or reruns every recording with another model (which changes the room's setting). Jobs wait while recording, so running later is the default.

### Apex matches

Finds match ends from key frames, scaled down to 64 by 36: the result screen, a gray picture with a red banner across it, marks the end where it first shows; ends closer than 150 seconds count once. Moment events of kind `match_end`, tagged `match`. Match ends are the same for the whole squad, so it runs once per set.

## Transcription

A plugin that turns each member's voice into range events of kind `speech` with whisper.cpp (its Windows CLI, on half of the cores) on whichever member runs the job. Settings: model (small, base, medium, large-v3-turbo) and language (auto or a fixed one). The tool and the chosen model are downloaded on request. Shown as subtitles on the video (switchable) and as a conversation list that scrolls with playback and seeks on click. whisper runs without carrying text from one window to the next (`-mc 0`), which stops it repeating a line forever. Before it, ffmpeg levels the speech (`speechnorm`) and then finds silence (below -45 dB for at least a second), so a quiet microphone is not taken for silence; a line with less than a quarter second of sound under it, or one that repeats (or only adds a trailing word to) one of the eight lines before it, or that already appeared three times, is dropped. whisper also runs with `--suppress-nst`. When a job finds no line, its `done` record and the log say how many lines whisper returned and how many were dropped.

## Health check

Opening a member's detail pane runs that member's local check (Windows build, capture, app sound, encoder, relay and UDP) over the existing connection and lists the results; Check again repeats it. The lines come as a message with `{name}` slots and arguments, never as device names, and each viewer translates them.

## Recordings on this PC

Settings > Recordings shows a bar of the space this app uses, other files and the free space, the size per hour (from the newest recordings) and how many hours of recording still fit; the sidebar warns when fewer than the chosen number of hours fit (10 by default). Recording stops when the disk is nearly full. Nothing is deleted automatically. Settings > Recordings lists each one's length, people and size here, with None and All but newest 3 to select; Delete videos… lists exactly what goes (each recording and each member's part with its size) and says for each whether it goes completely or others still have it.

The list is every recording of the room, from the logs. Each row is in exactly one of two states: On this PC (media is here) or Not on this PC with a Download button, and always shows its size: the size on this PC, or the download size when it is not here. Pressing Download fetches the recording from whoever holds it and the row shows the progress like any receiving; nothing else fetches a finished recording. A row that is not here cannot be opened, played or exported.

The sidebar list holds only real recordings, all of them, scrolling by itself. While idle, the box with the record button says Standby and how many are online (it opens Live); while recording the button becomes Stop recording with a red dot and the elapsed time, and the running recording is pinned on top of the list (a red dot and a red outline on its picture), then every recording. The Recordings header above the list opens the full view in the main area. Each row has a small thumbnail with the members' faces over its corner, the time or title, the length with the Debrief and Imported marks and its state and size; only the open row has a background. The Recordings view shows every recording as 16:9 cards in one newest-first list, without date groups, with a text filter and Import… at its top, and Export and Delete on each card. A thumbnail is one frame from the middle of the first view that is all here (this PC's own first), made with ffmpeg within seconds after a recording ends or is imported, or later if it is missing; it is `rooms/<room>/thumbs/<recording>.jpg`, served as `ezh:thumb/<room>/<recording>`, removed with the videos, and recordings without a picture (voice only) show an icon. Open folder opens the recording's own folder under `recordings`.

## Export

Export video… (Recording menu or a recording row) writes one video on this PC, like a screen recording of the player: the set's players on the auto grid with names, lined up as in playback; track 1 is the mix and one track per player (app sound and voice) follows. The app streams each part's segments to ffmpeg over localhost. Players with nothing here yet are left out. Each tile is as wide as the widest player's picture (the whole video at most 2560 by 1440), and the bit rate is the sum of the players' bit rates, turned into H.264 terms, but no more than the preset rule gives for the video's size: the export cannot hold more picture than its sources. The video is written in the data folder first and then moved into place, so an existing file is replaced only by a finished one.

## Import and export of recordings

The format is described in [session-format.md](session-format.md). The app's storage does not change; this is only the way in and out.

- File > Import recording… (or dropping files or a folder on the window) makes a recording from video files or from a session folder. `session.rs` parses and checks `session.json`, `notes.csv` and WebVTT (plain functions with tests, including malformed input); `import.rs` plans the import and converts. The dialog shows the title and a name for each view. One import runs at a time and the notice above the page shows its progress with Cancel. Nothing appears in the list until every view is converted, and a problem stops the import and removes what was written.
- ffmpeg reads each file once and writes the same layout a capture does: an `init.mp4` and segments of 4 fragments of one second, each hashed and logged. A picture the app can play is copied (H.264 and VP9; HEVC and AV1 only when every member can play them) and anything else becomes H.264 (libx264, one keyframe a second); sound is copied when it is AAC, MP3, Opus or FLAC and otherwise becomes AAC. A file with sound only, or a separate voice file, is a voice (`m`) series. Times start at 0 in every view.
- Every view is a made-up member of the room, because a recording holds one file per member and a log is one per member: a new key whose log the importer writes (`rec` with the extra fields `imported` (the importer's ID), `view` (the name) and `title`, then `cap`, `seg` and `rec_end`). The importer also logs a `remove` record for it and keeps it among the room's removed people, so every member pulls its log and files like any other, nobody dials it, and it is not listed as a member. Its name, the Imported mark and the importer come from its `rec` record; its clock offset is the importer's, so its views line up with the importer's notes on every PC. The importer holds the files, and the others fetch them from it when they press Download, like any finished recording; the importer is named on the recording. Deleting works as for any recording.
- Notes, marks, chapters and subtitles of the folder are `event` records in the importer's log (notes and marks at a moment; chapters as ranges; subtitles as `speech` ranges on that view), attached to the recording like notes written in the app.
- Players show the title (the recording list and header) and an Imported mark on the recording and on each view's label. Plugins read imported views like any file; Transcription reads the view's sound when it has no voice series.
- Export to folder… (Recording menu or a recording's menu) asks for a place and writes `<recording>` there: one plain mp4 per view fed from the stored segments over localhost (copied when the view is one continuous part; several parts or a late start are placed on a black, silent timeline by a filter graph and encoded once), `<name> voice.m4a`, `session.json`, `notes.csv`, `chapters.vtt` (people's chapters and the Apex matches) and `<name>.vtt` (spoken lines). By default each file keeps its own start and `session.json` gives its `offset_ms`; Start every video together pads late files so every offset is 0. Only one export runs at a time, whether it is the combined video or a folder.

## Deleting and cleanup

- Delete… on a recording removes this PC's videos of it, files deleted for good (not the recycle bin), and cancels this PC's queued or running analysis jobs on it. The confirmation lists what goes and has two forms: This deletes it completely, or Others still have it. Which one is decided from the last reports of every other member of how much of the recording each holds (the counts the members already exchange); offline or never-contacted members are not special-cased. If nobody else holds any part, the recording is removed completely: this PC's media goes and a `set_del` record in the log makes every member drop the entry, delete any leftover media and thumbnail, and hide its job rows and the results and notes attached to it. Otherwise the row stays as Not on this PC with Download, and job rows and results stay (they belong to the room).
- A recording of 30 seconds or less asks Discard this recording? right after the one who stops it confirms the stop; discarding removes it completely, as above, whatever the reports say.
- A recording that is being recorded or exported cannot be deleted. Notes, drawings, debriefs and the game plan of a recording that is only deleted from this PC stay.
- Files go only when asked: Delete… (the recording's folder and thumbnail on this PC), a `set_del` from deleting completely or discarding (the same on every PC, retried while the folder is there and skipped while this PC records that recording), Leave room… (the room's whole folder, removed again while the app runs if a write still under way brings part of it back) and Help > Reset app. Besides these the app removes only temporary files: live segments in `standby/` beyond the newest few, the whole `standby/` at start, a `.part` without a whole fragment, a fetched copy that fails its check, partial exports, and reports and old logs older than a week. Nothing else is removed at start or on a timer, so a restart never removes a recording, and it never touches events or the key without being asked.

## Diagnostics

Help > Diagnostics is the one place for this, with tabs: Summary (one line per area with ✓, ⚠ or ✗: connections, capture, microphone, transfers, storage, versions, clocks, plugins), Where data goes (a first box that is green when every member is direct and amber when any goes through a relay server, with the relay and download hosts, the address lookup, the update check to github.com, downloads in progress and the local API when it is on; then a diagram of this PC and each member, direct or through a relay server whose name is shown while the content stays encrypted, and a table of what goes to whom with the bytes sent and received), PCs (per PC: graphics card and driver, encoder in use with its codec, CPU, memory, display size, Windows version, and while recording the captured frames per second and the dropped frames; for this PC the Windows time service and its last sync, for members the clock against this PC, and the clock difference between each pair of members), Traffic (what is moving now and a count of this run's transfers by kind and result), Log (the newest lines of `log.txt`, addresses hidden) and Jobs. Copy report and Save as file… give one plain-text report: the summary, the version, OS, check, connections and paths, transfers, recent events and errors, the hardware and clocks, where data goes, the jobs and the recent log, with names, IDs, addresses and file paths always removed. There is no separate developer window. The `debug_view` and `debug_report` commands remain for the Diagnostics tabs and the end-to-end test, and the local API's `GET /v1/diagnostics` gives the same report.

Help > Reset app removes settings, downloads and logs and restarts; keeping the ID, rooms and recordings is ticked by default.

The text log `log.txt` has the local date and time on each line and logs joins, recordings with their segment counts, captures, exports, updates, plugin jobs, connections and path changes, and errors; it rolls over at 10 MB into `log.old.txt` and `log.older.txt`. A run of failed connection attempts to one member is logged once and, when it ends, as a count; the networking library logs only warnings. A crash also writes `crash.txt` at once, which the report includes.

Memory is bounded: the last 1500 transfers (about five minutes of a full room of six), 500 connection events, 120 cut segments (four minutes of both series), 200 ffmpeg lines; the Log tab reads at most the last 256 kB of `log.txt`.

Hardware: `src-tauri/src/hw.rs` reads the graphics cards, CPU, memory and Windows version once in the background (PowerShell, CIM) and the display size from the capture library; it never reads device names of microphones or headsets, user names or paths. The `hello` message carries a small `hw` object with those values, the encoder in use (NVENC, AMF, QSV or software, and the codec) and, while recording, the captured fps and dropped frames; it is resent every few seconds, so members see the rate change. Receivers keep only known keys, with lengths and ranges limited, and an older member without `hw` shows as not shared. Captured fps counts frames the screen delivered; a dropped frame is one that the encoder pipe had not taken before the next arrived, so dropped frames with a healthy network point to a stalling sender.

Clocks: each member's offset is the existing ping estimate (`offset_us`, theirs minus ours); pairs of members are the difference of two offsets. The Summary shows a warning when the largest difference exceeds 3 s or when the Windows time service is stopped; the PCs tab also warns when the last sync is more than 14 days old. The service state comes from `sc query w32time` and the last sync from `w32tm /query /status` (the date in either year-first or month-first form), refreshed every 5 minutes; when either is unavailable the line reads unknown and does not warn.

Two log lines only: a slow send (one write to a member took 1.5 s or more, with the number of sends queued for that member; at most once per member per 30 s) and the capture rate (once when the encoder falls behind the capture, again only after it recovered, and a line when a recording of at least 5 s ends with its average fps and dropped frames). Both are warnings, so the report's recent errors list them.

The report has `hardware`, `clocks` and `where data goes` sections, with relay hosts, names and addresses removed like the rest.

## Local API

- A small HTTP server inside the app (`src-tauri/src/api.rs`, on `std::net`, no framework) lets a person, an AI agent or another program read a room and write to it. It is off by default; Settings > API has one switch, the address, Copy token (New token replaces it), the access choice and the endpoint list with an example each, read from the embedded `llms.txt`. The switch and a random token are kept in `settings.json`. It starts at launch with `--api` (or `EZH_API=1`) and writes its address and token to `api.json` in the data folder (current user only) while it runs. It binds `127.0.0.1` on port 47625 (`EZH_API_PORT` changes it for tests), or all interfaces when Settings > API > Access is Other devices (with a warning in Settings and on the API badge in the sidebar), takes one request per connection, and refuses a `Host` header that is not the loopback address, or with Other devices this PC's own IPv4 addresses or name, plus the port (DNS rebinding) and any request without `Authorization: Bearer <token>` (the token is compared in constant time). There are no CORS headers. `GET /llms.txt` needs no token and contains no secrets.
- It reads and writes the same room-log records the UI uses. Reads: rooms; a room's recordings with members, start, end, length, kind (play or debrief) and, for an imported one, its title and importer; a recording's events (notes, marks, plugin results) with tags and times in seconds from its start; match chapters (the Apex plugin's match ends); transcript lines; the game plan; plugins and jobs. Writes: a note or mark on a recording (an `event` record, so tags work like `#tag` in the app) and a new game plan (a `board` event). Writes go only to the open room, because only that room is shared; the app then sends the record to the others like any note. No new record kinds and no storage change. Two calls move whole recordings: import (from a session folder or video files) and export (to a new folder), both on this PC's paths and answering when they are done. Clips are not part of it.
- The handlers work on plain room logs through a small `Backend` trait, so their tests need no app. [api.md](api.md) lists each endpoint with its request and answer; [llms.txt](llms.txt) is the same in short for AI agents, embedded in the app at build time and served at `/llms.txt`.
- The AI button (in every page header and the player header) opens a menu of three purposes (write notes from the transcript, summarize a recording into the game plan, find the mistakes in a match). Choosing one copies a plain-text prompt in the app's language with the API address, the token, a pointer to `/llms.txt`, the room and the recording; with the API off, the menu offers to turn it on.

## Updates

Two channels: Stable reads `latest.json` and Beta reads `latest-beta.json` on the `updater` release; Settings > Updates chooses (Stable by default). Every release goes to Beta; a release whose version has no pre-release part (0.9.1, not 0.9.1-1) also goes to Stable.
