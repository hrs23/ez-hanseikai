# Design

What the app does and how, as built. What is decided but not built is under [Planned](#planned).

## Shape

- A Windows app, the same for everyone. Tauri: a Rust core that captures, encodes and syncs; a web UI. The window keeps the standard Windows caption buttons and, on Windows 11, its title bar, border and text take the sidebar's colours (`DwmSetWindowAttribute`; ignored on older Windows). Closing the window quits the app, asking first only while files arrive or an export runs; minimizing keeps it in the taskbar. One app runs per data folder: a second start brings the running window to the front, and an app on the same folder from another build says so and exits (a lock file `app.lock` in the data folder; one left behind by a kill or crash is only logged, and the app resumes on its own).
- One window: a left sidebar that is the room, and a main area for what is chosen there. No tabs and no top bar. A native menu bar (File, Room, Recording, View, Help) mirrors the commands. Each action and piece of information has one place, with no explanatory text; status sits next to what it affects. Logs stay in the diagnostics window.
- The sidebar, top to bottom: the room's name with a ▾ (long names end in an ellipsis; the menu holds Room settings…, Copy invite code (and Cancel invite while one is open) and Leave room) and, under it, the members' faces (green dot online, an amber dot on a member who is not recording while this PC is, faded offline; a face glows while that member speaks); four items, Live, Game plan, Members and Extensions, each marking the page open in the main area, with a count for join requests on Members; the record box (the quiet Start recording button with a red dot, ▾ with Switch to debrief, and under it Standby and how many are online); the list of every recording, newest first, scrolling by itself; a warning when free space runs low; and at the bottom the Screen and Microphone buttons and the own row (name, short ID, a Via relay badge that opens where data goes and shows only while a connection uses a relay, and the settings gear). The API badge, while the local API is on, sits at the top right beside the AI button and opens Settings > API. Room-wide things are above, personal ones at the bottom. The sidebar's width is dragged at its right edge (double-click resets it, the arrow keys move it), kept between 220 and 420 px and remembered on this PC; nothing in it ever scrolls sideways, and long text ends in an ellipsis. Ctrl+1 to Ctrl+4 open Live, Game plan, Members and Extensions; Ctrl+B hides the sidebar; Ctrl+, opens Settings.
- Shared and personal stay apart: the room part of the sidebar and the player's outlined region are shared; the bottom of the sidebar, Settings and the player's own controls are personal. Destructive actions say whether they affect only this PC or everyone. Confirmations are in-app dialogs; file pickers and the few native message boxes come from the Windows dialogs.
- Capture and Settings stay apart, as in Discord, OBS and Zoom: what is touched every evening (the screen, the app whose sound is recorded, the microphone, their meters and volumes) sits in small menus on the Screen and Microphone buttons; what is set once (name, language, ID key, quality and upload limit, shortcuts, recording sounds, recordings on this PC, the local API, updates) is in the Settings window. One page holding both would put the meters next to rarely used settings and take the user away from the player to change the microphone.
- Everyday review features live in the app: recording, sharing, rooms, playback, notes, drawing, Watch Party, export and showing events. Game-specific analysis lives in extensions. The UI says "app" for capture sources and their sound; game terms such as matches come from extensions as tags and chapters.
- Nothing goes to a cloud. Everyone is equal: no host and no leader for recording or playback.
- English and Japanese, following the Windows display language until one is chosen in the settings. The UI looks up each English string in one dictionary (`ui/i18n.js`), so fixed messages from the core are translated the same way; the core sends codes for notices that carry values. The native menu, message boxes and notifications have their own small table.
- One icon set (Lucide, inlined in `ui/icons.js`) and one set of design tokens in `ui/style.css`.
- Each member has a colour, the same on every PC: members (and removed members) sorted by ID take the palette in order. It marks their avatar, notes and drawings.

## Identity

One key per person, made on first start; its public half is the person's ID everywhere. The name can change; the ID cannot. Moving to a new PC means exporting and importing the key (File menu).

## Rooms

- Without a room the window shows the start screen: the name, the recent rooms with Enter (the most recently used first; ⋯ offers Delete…), Join with a code and Create room. While a join waits for approval it shows that, with Cancel.
- One room is open at a time; entering, creating or joining another leaves the open one first. Leave room (in the room menu) returns to the start screen without asking and keeps the room and everything of it on this PC, and Enter there goes back in. Delete… on a room in the start screen's list asks first and removes the room and its data from this PC, but not while a recording of that room is exported; coming back needs an invite code. Other members keep theirs.
- The room opens on Live. The main area shows the page chosen in the sidebar, each with a header (its title, the member count on Members, AI). Members is a table of everyone with their ID, one short status, direct or relay connection, round trip and version (another version in the warning colour), with join requests and an open invite above it. The status is exactly one of Not sharing, Standby (sharing) or Offline with the last time they were seen; the connection cell opens where data goes. Recordings are described under Recordings on this PC. Room settings (a dialog from the room menu) holds the room name. A member's detail pane shows the connection (the relay server's name when relayed, round trip, bytes sent and received, clock offset, version), what this PC is receiving from them, their check results and Remove from room. Checks run on their own when the pane opens and again on request. Game plan is described under Events; Extensions are described under Extensions.
- Invite codes work once, only while the inviter's app runs, and can be cancelled. Creating a room copies an invite code. Any member can invite.
- Any member can rename the room (room menu > Room settings…): a `room_name` record in their log; the newest (by each log's clock offset) wins everywhere; a rename is stamped after every name already known, so a member whose clock runs ahead cannot undo it. An extension's settings change is stamped the same way.
- A room is meant to be kept and reused, so its history builds up; a new room starts with its own empty history.
- Joining needs approval: someone using a code asks to join, every member online sees a row "<name> wants to join" with Approve and Decline in the Members list (and a Windows notification while the window is minimized), and nothing of the room is sent until a member approves. The request ends with the invite.
- Any member can remove a member for the whole room: the removal is a record in the remover's log, so it reaches everyone; everyone stops sending to them from then on and refuses their connections, and everyone sees who removed whom. What they already received stays with them. A later approval lets them back in.

## Live and recording

- The Screen button at the bottom left (like Discord's) shows what is sent: Screen off (dashed), or the window or display and Standby (green; nothing under it while recording, because the record button is the one place that shows recording). Clicking it when off or when its source closed opens the picker; clicking it when on turns the screen off. Its arrow opens the picker: windows, displays with their size, Turn screen off, and the app sound's meter, volume and mute (the sound is the chosen window's, or the whole PC's except this app for a display). Every start except the restart after an update begins with no source and the microphone muted, so nothing is sent until the player chooses. A capture problem shows on the button. A shared window that closes is a screen that went off: the capture and the live picture stop, a recording goes on with the voice in a new part, and the button and the own tile say Capture source closed; choosing a screen, or the same window coming back, starts a new part with the picture. The app never moves to another window of the same program (only the same window may change its title).
- The Microphone button mutes and unmutes and shows the same states as Screen: muted (dashed) or on (green), with a level meter inside it; its arrow chooses the microphone and shows its meter, volume and mute. The microphone is its own track and muted at every start except the restart after an update. The volumes of app sound and microphone are kept on this PC. App sound comes from per-process capture: a window's own sound (its process tree), or for a whole screen the sound of the whole PC except this app, so a voice chat is on the app sound of a screen source.
- Inside a room everyone's picture and sound stream all the time while their screen is on; Live (the first sidebar item, where the room opens) shows a tile for every member of the room, in the saved order and then in join order, before any recording exists, while nothing records and while a recording runs. A tile shows the picture while the member shares a screen; a member who shares nothing gets a quiet hatch and an offline member a darker one with a grey face; the own tile is one Select screen button while no screen is chosen. While this PC records, a tile tells at most one problem (Not recording screen, No voice for 1 min when the newest voice segment is older, or n s behind when the newest picture segment lags), from the segments already in the logs. While this PC records (not a debrief), a recording opened in the player stays paused until the viewer presses play, whichever way it was opened or followed. Turning the screen off stops only the live picture: recordings already made are sent as before. The upload limit (Settings > Capture) caps the upload. When a recording starts, every member's window opens Live. A member who is speaking (the microphone level is over a threshold, with a 300 ms hang, while recording and unmuted) gets a ring on the face and on the tile name: the speaker sends `speaking` with `on` true or false only when it changes, and `false` when the recording stops.
- Live tiles, idle or of the recording in progress, play the whole room in step at one shared delay on the wall clock: the delay grows at once by holding every tile on its frame when a member's media has not arrived yet, and shrinks slowly by playing at 1.05× while the shared moment trails the slowest holding member's loaded end by more than 5 s (2 s of headroom plus a 3 s gap). A member whose media is more than 12 s old no longer holds the room; once the shared moment passes their media their tile shows "Waiting for {name}…" over its last frame until it catches up, and while nobody holds the shared moment runs on at real time. Only a member whose newest part has a picture holds the room. A live picture whose start is not known yet (from an older version) plays at its own edge.
- The unit is a recording, one per room: anyone's Start recording (the sidebar button or Recording menu, after a confirmation) starts it for every member (a Start that meets a recording already running, such as two members pressing it together, leaves that one running) and anyone's Stop recording (also confirmed) ends it, with no shortcut key. Leaving the room, exiting (without asking), an update, a full disk or Reset ends only your part (after an update the app comes back into the room with the screen and microphone it had), and Start recording is refused while the disk is almost full; the list shows a recording as ended, and it can be exported, once no member who is present (connected, seen within a minute, or never seen in the first minute after this app starts) still records it, and coming back to a room that still records rejoins it. Every member sees "Aki started recording" or "Ren stopped recording" in the app with a short sound (Settings > General turns the sound off); there are no Windows notifications. Every member sees the same list. Nothing is kept while nobody records. A member with the screen off records only their voice; a member who joins mid-recording records from then on; an absent member is an empty tile. While recording, the Stop recording button shows a red dot and the elapsed time, and the first row of the recordings list shows a red dot, Recording and the current match (or who started it) and opens the player at the latest moment; the record box shows Standby and how many are online while nothing records, and opens Live. (Records and code call a session a set.)
- Mark this moment (Recording menu or a global hotkey, Ctrl+Alt+M by default and changeable in Settings) logs a `mark` event at the current time of the recording. The hotkey is registered with Windows only while recording and never touches the game.
- The capture is scaled down to the quality's width and converted to NV12 (BT.709) on the GPU before it reaches ffmpeg, or on the CPU when the GPU cannot. One ffmpeg process per person encodes it once into two fragmented MP4 series that it sends to the app over localhost: `v` (picture and app sound) and `m` (voice). Each fragment is one second. The app cuts them into segments of 4 fragments, and also at once on Record and Stop, so a set starts and ends on a fragment. Four seconds keeps a live joiner close to now and keeps the file count low (about 900 per hour per series). Live and recording are the same segments: a recording is the list of segments logged for the set.
- A capture is one encoder run; a restart (new size, codec or quality, or a crash) starts a new capture, so a set can have several parts per member. A new size or quality waits until no set is recording. An encoder that exits, or gives no output for 10 s while frames keep coming or a frame write does not return, is stopped and restarted into the same set; after three failures in a row without a minute of output it is skipped for ten minutes for the next working encoder (another backend of the same codec first), down to libx264. The old ffmpeg is stopped before the next one starts. Which encoders work is probed once, each probe with a time limit, and kept until ffmpeg or the GPU driver changes. Until the new encoder gives output, the preview and the own row show the problem and the own tile does not show recording. Screen capture never waits on ffmpeg (a feeder thread per capture writes only the newest frame), and sound writes to it time out.
- Quality presets, each with its width at 30 fps: Light 960, Standard 1280 (the default), High 1920. The height follows the source's shape and nothing is scaled up. The bit rate is 0.2 bits per pixel per frame of the preset's 16:9 size for H.264, times 0.7 for HEVC and 0.55 for AV1 (Standard: 5.5 Mbit/s H.264, 3.0 Mbit/s AV1). Capture shows the resolution, frame rate, bit rate and codec in use.
- Meters show the level after the volume, in dB from -60 to 0 like OBS: green, yellow from -20 dB, red from -9 dB, the highest peak held for 1.5 s, and a clip mark for 3 s after a full-scale sample.
- Codec: AV1, then HEVC, then H.264, the best one that every member can play. A keyframe every second, no B-frames. There is no separate full-quality copy.

## Data

- Each person writes only their own append-only files: a log per room and their recordings. Everyone keeps every member's log of the room and receives the recordings, so the room survives anyone leaving. The logs are the source of truth and everything shown is computed from them. [session-format.md](session-format.md) describes the files, the records and how views are derived.
- After a crash, each own unfinished segment is cut back to its last whole fragment, finished and logged, and an open set gets its `rec_end`; if the set is still recording elsewhere, the member joins it again. A Stop is a `rec_end` with `stop`, so a member that missed the message ends the set when it finds that record in any log.
- The app works from an empty data folder, and recreates its files if the folder is deleted while it runs; without `key.bin` it makes a new identity at the next start and says so.

## Sharing, verification and time

- Peers connect directly with iroh, through a relay when they must, with encrypted connections accepted only from room members; the messages are in [protocol.md](protocol.md). Either member may dial; when two connections exist, the one dialed by the lower ID is kept. A lost connection is redialed with a growing wait after a failure.
- On connecting, members pull every member's log, so late or offline members learn every recording (the list), though not its videos. The recording in progress is received on its own; a finished one that is not on this PC is fetched only when its Download button is pressed.
- Order of importance: logs, voice, live picture, then history. The upload limit caps the upload; history always keeps a quarter of it.
- Each recorder logs the size and SHA-256 of every init and segment. A fetched copy is checked once, when it arrives, and a copy that fails is deleted. The set list shows whether everyone has everything or what is missing.
- Every PC asks time.cloudflare.com for the time at start and every hour, and peers measure each other's clocks; playback lines up everyone in a set from these, with a manual nudge.
- The player and Live read media through the app's `ezh://` scheme, which serves each part's index (its segments here, with their times), its init and each segment; the page plays them through Media Source Extensions, one element per tile and voice for its whole life, appended with the segments around the shown moment, so a seek is a fetch of one segment however far it goes.

## Player and Watch Party

- One player shows the live tiles (Live), the recording in progress and past recordings. Its header has the title, chips (Recording with the timer, or Recorded or Imported; the one sentence of the view line while a video is missing or coming; Debrief n times · m min, which exports each debrief as a folder), the length and matches, the Watch Party control and the side panel button. Below it the shared region holds the views and drawing tools, the tiles and, along the bottom like YouTube's, the chapters, event marks, seekbar and one bar of controls: play, back, forward, volume, time, the current match (opening a list of matches), Latest or Jump to latest, Note, volume per member, subtitles, speed, layout and full screen. The region is outlined in the accent colour while Watch Party is on.
- At the latest moment of a recording in progress the seekbar is red and the bar shows ● Latest; further back the header says how far behind the latest and the button reads Jump to latest −2:14. The end of the recording in progress grows with a dashed red tail.
- The side panel has three tabs: Review lists the analysis that is not done (waiting for a PC, receiving, running, or failed with Retry), then the matches, each with its notes, marks and match end and a Watch button, with A/D and Q/E as hints, then Write to the game plan; Notes lists every event with the filter, and a note added through the API carries an AI mark; Talk is the transcript.
- Each person plays their own copy. After Play or a seek every tile waits for the others (at most a second each), so all start together. Views: all players, or one player's picture and sound (keys 0 and 1 to 6).
- Layouts: a two-tier picker chooses the number of places (1 to 6, never fewer than the players present; the rest stay free) and then auto grid, one large with the others beside or below, or a row. Dragging a name label swaps two players. The recorder's layout is the set's default; each viewer can rearrange.
- Click toggles play, double-click shows one player, F is full screen. Shortcuts (View > Keyboard shortcuts): Space/K, arrows and J/L to skip (Shift and Ctrl+arrows for longer), < > for speed up to 3x, Shift+P/N for the previous and next recording, Q/E for notes, A/D for a minute before the previous or next match end (other events and chapters when there are no matches), C for a quick note, X to clear drawings, Ctrl+Z to undo the last seek or deletion.
- Watch Party follows the recording each member has open: a member follows the shared state only of the recording they are watching, so opening another recording leaves the party for that member alone, with no question and no message to the others, and the row of the recording they left shows Back, which opens it again and rejoins. Outside it the header shows how many watch with a Join button; inside, the number watching and Leave; a recording's row in the sidebar shows how many watch it. One shared state holds the set, playback (playing, position as wall time, speed), view, layout and tile order; it is ordered by a Lamport counter, then time, then sender, the newest wins, and it is repeated every few seconds, so anyone who joins catches up. Opening a recording while in the party joins what the others watch there and never moves them: a state from joining has counter 0 and the negative join time, so any action and any earlier join wins over it. Each message also carries how many records of each member's log the sender holds. Those counts only grow; everyone shows only events below them, fetches what it lacks at once, and shows "Catching up with Ren" to all until it has it. A member without the files fetches that recording first and shows the one sentence of the view line on the tile. When someone else plays, pauses or seeks, their avatar marks the place on the seekbar and a line says who did what; Ctrl+Z undoes the last seek. Volume stays personal; outside Watch Party the layout is each viewer's own. An older version that switches recording inside the party is ignored by a newer one and still looks like a normal party to it.
- Each tile plays its picture and app sound and, as a separate audio stream on the same clock, its voice. Everyone's voice is heard in every view; app sound comes from the chosen player, and in All players from the viewer's own player (the first one when the viewer did not record). The player starts with sound on at full volume, whatever the microphone muting at capture start, and the page plays sound without needing a click first.
- Volume is personal: one volume and mute for the player, and app sound and voice volume and mute per member (from the control bar or a player's name label), kept on this PC.
- Hovering the seekbar shows the frame of the shown player at that time (a hidden slot plays there), and the chapter.
- Sync status sits on what it concerns (downloads of the video tools and of extension models show the same percent, speed and time left above the page): one sentence, the view line, names the first member who blocks playing every view: Ren's video missing · Download, Receiving Ren's video · 2 min left, Koya's video is only on Koya's PC, or Koya didn't record a screen. It is shown on the recording row, in the player header and on a tile that has no video. A recording row also shows this PC's receiving with percent and speed, the analysis (Analyzing 42% or Analysis failed) and an export; while Watch Party is on, the stage shows who is catching up.

## Debriefs

- A debrief is a recording of voices only, made while watching another recording. The record button's ▾ menu has Switch to debrief (and Switch to recording back); the button then reads Record debrief, and it does so by itself inside a Watch Party. Every member records only the voice series (`m`); the `rec` record and the start message carry `voice`, and `of`, the recording that was open in the Watch Party, so members who join later record the same way. `start_recording` takes `debrief`; without it the app decides from Watch Party. Both ask first, and the debrief question says that only the voice and the viewing flow are recorded. While it runs the header shows Watch Party and a Recording pill.
- A debrief links to its recording through `of`. An older debrief (voice only, with `party` records) links through the recording named by its first `party` record; one with neither stays a normal recording. A linked debrief is left out of the sidebar list, and a debrief whose recording is gone is a normal recording again. The recording's header shows Debrief n times · m min; clicking it exports each debrief as a folder, a voice-only [session folder](session-format.md) with `watch.json`.
- While any recording runs, each member logs the Watch Party actions they make as `party` records (the set being recorded, the time and the shared state), and the starter logs the state at the start. These are the only traces Watch Party leaves. There is no debrief player: the folder and the local API (`of`, `watch` and the voices of a recording) are how a debrief is read, by people with a video editor or by an AI agent.
- Deleting a recording also deletes the debriefs that name it in `of`, each through the same delete (so each keeps a copy that others still hold). After a debrief ends, Summarize with AI copies a prompt that names the debrief and the API.

## Events

Notes, markers, drawings, board cards and extension results are one kind of record, an event: who made it (the person whose log holds it, or an extension name and version), its kind, an optional target (a moment, a range, a file or the whole set) and its content (text or numbers), with tags (people write `#tag` in a note; extensions tag their own). Only people's events can be edited or deleted, and a deletion can be undone. A moment belongs to the room, so every set covering it shows the event; clicking one seeks everyone in Watch Party. The app makes notes, drawings and board cards; other kinds come from extensions.

The Player shows every event by its shape, never by extension:

- A moment: a mark on the seekbar, a row in the event list, and, with text, a line over the video for 8 seconds.
- A range on one member's file with text (such as speech): a subtitle on that member's tile (CC switches it) and a line in the Conversation list, which follows playback and seeks on click.
- Any other range: a chapter above the seekbar and a row in the list.
- Moments an extension tags `match` are match ends: the chapters between them are "Match 1, 2, …" (the open one only while recording), and the current match shows beside the clock.

The filter above the list searches text, names and kinds, and `#tag` (or clicking a tag) lists that tag's events, in this recording or, with its scope, in all recordings of the room. A quick note (C or the note button) pauses, opens a box over the video at that time (Tab: without a time, or completes a tag), and Enter adds it and resumes; while it is open others in Watch Party see "<name> is typing". Right-clicking the video copies a link to the moment and view (`ezh://moment/<set>/<seconds>/<member>`); links in notes and on the board open it in the app.

The game plan (the Game plan item) is one board for the room: a big team card on top and, below it, a card for each member in a row, in the order of their `pos`. Anyone can add a card with a title, rename it, drag it to a new place or delete it. Each card is a `board` event with `values` `{card, title?, pos?, gone?}` and its text; for each card the newest event wins (by each log's clock offset). `card` is `team`, `m:<member id>` or an id the app made; an event without `card` is the team card, so older versions keep reading it. A card's text is short Markdown, rendered as DOM nodes from text only, never as HTML: the first line is bold, then headings, bold, italic, strikethrough, ==highlight==, inline code, bullet and numbered lists, links and `#tags`. Links open only when they are `https:` or `http:` (in the default browser, through the app, with characters outside ASCII percent-encoded; a link whose text does not show its host, or whose host has characters outside ASCII, asks first, naming the host) or a `ezh://moment/…` link (in the player); anything else, images and raw HTML stay as plain text. The pencil edits one card (Ctrl+Enter saves, Esc cancels) and an empty card shows a quiet Write button. The board is laid out at a fixed width and zoomed to fit, with − and +; full screen (F) scales it to fit one screen, and the window button opens it in a second borderless window (`index.html?board`) that follows the same events and nothing else. `put_board_card` writes a card, filling what it is not given from the newest event, and `GET /v1/rooms/{room}/board` reads the team card.

## Drawing

Part of the app. Drag on a paused frame to draw: pen, arrow and a laser that fades (the laser works while playing too), X clears, one colour per person. Points are kept relative to the drawn player's picture, so strokes stay in place whatever the layout. In Watch Party strokes go to everyone as they are drawn; finished pen and arrow strokes are kept as `drawing` events (player, tool, points, moment) and show whenever playback is paused at that moment. Clearing hides the strokes at that moment for everyone until playback moves on.

## Extensions

- Analysis only: an extension reads recordings (picture and sound) and set information and writes events, plus an optional tag dictionary (tag to display name). It has no UI; the app shows every extension's events the same way. It never touches the game.
- Self-contained: its own program, depending on no other extension and turned on or off on its own. The app knows nothing about its internals. Each extension runs as a separate process of the app (`ez-hanseikai.exe --plugin`, idle priority; every child process of the app ends with it): the job comes as JSON on stdin (extension, settings, set and file information, duration, picture, app sound and voice as file parts plus a stream, the ffmpeg path, its own folder `plugins/<id>` and a scratch folder), and it answers with JSON lines on stdout, `{"progress": 0.4}` and finally `{"output": {"events": [...], "tags": {...}}}` or `{"error": "..."}`. Event times are seconds from the start of the file (`at_s`, or `from_s` and `to_s`); the app turns them into wall times.
- An extension declares an id, a name, a version, whether it may run while recording, its settings as lists of choices (the first is the default), and the files it needs for given settings (URL, SHA-256, size). Those are downloaded into `plugins/<id>` only when a member asks; until then that PC runs none of its jobs.
- Chosen per room with their settings: a `plugin` record holds the extension, on or off, the version of whoever set it, the settings and the runner; the newest wins. The runner is the `runner` field of the newest record, and when it has none, the member who wrote that record (the one who turned it on). If the runner is no longer in the room the extension has No runner and its row offers the choice. Only members with that version can run it. Each person only chooses which results to show.
- An extension whose result is about the whole set rather than one member (it declares so) runs once per set, on the file of the member with the most picture segments (the lowest ID on a tie), which every member derives the same from the logs; only that job's results are shown. Other extensions run on every file.
- One runner does the work. A job is one extension version and settings on one file (its key is `<plugin>@<version>/<settings hash>/<set>/<owner>`; a member's file in a set is read capture by capture, each as its `init.mp4` and segments in order, so a restarted capture adds no job; the extension runs once per capture and the results are joined). The state of an extension on a file is its newest `job` record by time over every key, owner and setting: `done`, `fail`, `claim` (running) or `retry` or nothing (waiting). The runner takes, newest recording first, every finished file of an extension that is on whose state is waiting, and whose segments it holds in full; a claim of its own that never finished is resumed first. It logs `claim`, runs it, writes the events and then `done` (or `fail` with the error). The runner receives the finished files that have video and still wait for an extension that is on (not the ones with a result, a failure or only voice), so a runner who joined late catches up. Of several `done` runs of a file the newest is shown (the lowest ID on a tie), and events of a run without `done` are never shown, so an interrupted run leaves nothing behind and reruns from scratch.
- Results do not depend on the current settings: a file that has a result, under any version or settings, is not analysed again, and changing a setting or the version re-runs nothing. Results show only while the extension is on. Re-run analysis on a recording logs a `retry` for each extension that is on, and the old result stays until the new one is done.
- The runner works one file at a time on finished files and stops when it records (unless the extension may run while recording), then goes on later. A run stopped on purpose logs `stop`, which reads as waiting again (older `yield` and `stop` records too). A job the runner claimed twice without `done`, `fail` or `stop` is logged as failed instead of being claimed a third time: one interruption can have another cause, two on the same job point to the job. Older versions still claim and run jobs, which can repeat work but never harms: the newest `done` is the one shown.
- A recording's analysis of an extension that is on (only files with a picture are analysed, so a debrief has none) is Failed when its newest record is `fail`; Waiting for the runner's PC while the runner is offline; File missing, a failure too, when neither the runner nor any member online holds the whole file (an old or deleted recording), so nothing waits for a file that may never come; Receiving while the runner fetches it from a member online; and otherwise Left. Retry logs `retry` and checks again.
- The downloader reports the bytes it has written (read from the partial file) so that the extension page shows percent, speed and time left.
- An extension's output lines are read up to 16 MB each, far more than any result; a longer line fails the job.
- Official extensions only, kept in this repository and bundled.
- The Extensions page lists every extension as a row, each collapsed at first (the open rows are kept on this PC): its name, a switch, one status line (3 left · Ren's PC, 1 failed · Retry, Waiting for Ren's PC, or No runner) and a small sample (chapters on a seek bar, a subtitle). Turning one on or off, or changing its settings or its runner, asks first and says it applies to everyone in the room. An open row shows the settings, the Runner choice (a member of the room), this PC's download with percent, speed and time left, and the recordings that are left or failed, each with its reason and Retry. A recording's row says Analyzing 42% or Analysis failed, the player's Review tab lists what is waiting or failed, and the recording menu has Re-run analysis. The raw job records are only in Diagnostics.

### Apex matches

Finds match ends from key frames, scaled down to 64 by 36: the result screen, a gray picture with a red banner across it, marks the end where it first shows; ends closer than 150 seconds count once. Moment events of kind `match_end`, tagged `match`. Match ends are the same for the whole squad, so it runs once per set.

## Transcription

An extension that turns each member's voice into range events of kind `speech` with whisper.cpp (its Windows CLI, on half of the cores) on whichever member runs the job. Settings: model (small, base, medium, large-v3-turbo) and language (auto or a fixed one). The tool and the chosen model are downloaded on request. Shown as subtitles on the video (switchable) and as a conversation list that scrolls with playback and seeks on click. whisper runs without carrying text from one window to the next (`-mc 0`), which stops it repeating a line forever. Before it, ffmpeg levels the speech (`speechnorm`) and then finds silence (below -45 dB for at least a second), so a quiet microphone is not taken for silence; a line with less than a quarter second of sound under it, or one that repeats (or only adds a trailing word to) one of the eight lines before it, or that already appeared three times, is dropped. whisper also runs with `--suppress-nst`. When a job finds no line, its `done` record and the log say how many lines whisper returned and how many were dropped.

## Health check

Opening a member's detail pane runs that member's local check (Windows build, capture, app sound, encoder, relay and UDP) over the existing connection and lists the results; Check again repeats it. The lines come as a message with `{name}` slots and arguments, never as device names, and each viewer translates them.

## Recordings on this PC

Settings > Recordings shows a bar of the space this app uses and other files, and one line, Free 120 GB · about 30 h of recording (the free space and the hours that still fit at the size per hour of the newest recordings); the sidebar warns when fewer than one hour fits. Recording stops when the disk is nearly full. Nothing is deleted automatically. Settings > Recordings lists each one's length, people and size here, with None and All but newest 3 to select; Delete videos… lists exactly what goes (each recording and each member's part with its size, and the debriefs that go with it) and says for each whether it goes completely or others still have it. When files of older versions are in the data folder, Delete old files (with their size) removes them after one confirmation; nothing else removes them.

The list is every recording of the room, from the logs. Each row is in exactly one of two states: On this PC (media is here) or Not on this PC with a Download button, and always shows its size: the size on this PC, or the download size when it is not here. Pressing Download fetches the recording from whoever holds it and the row shows the progress like any receiving; nothing else fetches a finished recording. A row that is not here cannot be opened, played or exported.

The sidebar list holds only real recordings, all of them (a debrief that names a recording is shown with it, not in the list), scrolling by itself. While idle, the box with the record button says Standby and how many are online (it opens Live); while recording the button becomes Stop recording with a pulsing red dot and the elapsed time, the only red in the app, and the running recording is pinned on top of the list, then every recording. Each row has a small thumbnail with the members' faces over its corner, the time or title, the length with the Imported mark and a count of the people watching, its state (the view line, the receiving bar with percent and speed, or the analysis) and its size; only the open row has a background. A thumbnail is one frame from the middle of the first view that is all here (this PC's own first), made with ffmpeg within seconds after a recording ends, or later if it is missing; it is `rooms/<room>/thumbs/<recording>.jpg`, served as `ezh:thumb/<room>/<recording>`, removed with the videos, and recordings without a picture (voice only) show an icon. Open folder opens the recording's own folder under `recordings`.

## Export

Export to folder… (Recording menu or a recording's menu) asks for a place and writes a new folder named after the recording: for each member one `.mp4` with picture and app sound (and `<name> voice.m4a`), the notes, the chapters and the spoken lines (and `watch.json` for a debrief), all lined up on the recording's start. ffmpeg reads the stored segments over localhost and encodes only what must be padded. Only one export runs at a time. The files are described in [session-format.md](session-format.md#export-folder). Recordings made by an older version's importer keep opening, with an Imported mark on the recording and on each view, and the importer named.

## Deleting and cleanup

- Delete… on a recording removes this PC's videos of it, files deleted for good (not the recycle bin), and stops this PC's running analysis of it. The confirmation lists what goes and has two forms: This deletes it completely, or Others still have it. Which one is decided from the last reports of every other member of how much of the recording each holds (the counts the members already exchange); offline or never-contacted members are not special-cased. If nobody else holds any part, the recording is removed completely: this PC's media goes and a `set_del` record in the log makes every member drop the entry, delete any leftover media and thumbnail, and hide the analysis state, results and notes attached to it. Otherwise the row stays as Not on this PC with Download, and the analysis state and results stay (they belong to the room). The debriefs that name the recording in `of` go the same way, each on its own check.
- A recording that is being recorded or exported cannot be deleted. Notes, drawings and the game plan of a recording that is only deleted from this PC stay.
- Files go only when asked: Delete… (the recording's folder and thumbnail on this PC), a `set_del` from deleting completely (the same on every PC, retried while the folder is there and skipped while this PC records that recording), Delete old files in Settings > Recordings, Delete… on a room (the room's whole folder, removed again while the app runs if a write still under way brings part of it back), Help > Reset app and the local API's `delete_set`, `remove_room`, `delete_old_files` and `reset`, which run at once without a confirmation. Besides these the app removes only temporary files: live segments in `standby/` beyond the newest few, the whole `standby/` at start, a `.part` without a whole fragment, a fetched copy that fails its check, partial exports, and reports and old logs older than a week. Nothing else is removed at start or on a timer, so a restart never removes a recording, and it never touches events or the key without being asked.

## Diagnostics

Help > Diagnostics is the one place for this, with tabs: Summary (one line per area with ✓, ⚠ or ✗: connections, capture, microphone, transfers, storage, versions, clocks, extensions), Where data goes (a first box that is green when every member is direct and amber when any goes through a relay server, with the relay and download hosts, the address lookup, the update check to github.com, the time check to time.cloudflare.com (amber while unreachable), downloads in progress and the local API when it is on; then a diagram of this PC and each member, direct or through a relay server whose name is shown while the content stays encrypted, and a table of what goes to whom with the bytes sent and received), PCs (per PC: graphics card and driver, encoder in use with its codec, CPU, memory, display size, Windows version, and while recording the captured frames per second and the dropped frames; for this PC its clock against true time, for members the clock against this PC), Traffic (what is moving now and a count of this run's transfers by kind and result), Log (the newest lines of `log.txt`, addresses hidden) and Analysis (the raw job records). Copy report and Save as file… give one plain-text report: the summary, the version, OS, check, connections and paths, transfers, recent events and errors, the hardware and clocks, where data goes, the jobs and the recent log, with names, IDs, addresses and file paths always removed. There is no separate developer window. The `debug_view` and `debug_report` operations remain for the Diagnostics tabs and the end-to-end test, and the local API's `GET /v1/diagnostics` gives the same report.

Help > Reset app removes settings and downloads and restarts, keeping the log; keeping the ID, rooms and recordings is ticked by default.

The text log `log.txt` has the local date and time on each line and logs joins, recordings with their segment counts, captures, exports, updates, extension jobs, connections and path changes, and errors; it rolls over at 10 MB into `log.old.txt` and `log.older.txt`. A run of failed connection attempts to one member is logged once and, when it ends, as a count; the networking library logs only warnings. A crash also writes `crash.txt` at once, which the report includes.

Memory is bounded: the last 1500 transfers (about five minutes of a full room of six), 500 connection events, 120 cut segments (four minutes of both series), 200 ffmpeg lines; the Log tab reads at most the last 256 kB of `log.txt`.

Hardware: `src-tauri/src/hw.rs` reads the graphics cards, CPU, memory and Windows version once in the background (PowerShell, CIM) and the display size from the capture library; it never reads device names of microphones or headsets, user names or paths. The `hello` message carries a small `hw` object with those values, the encoder in use (NVENC, AMF, QSV or software, and the codec) and, while recording, the captured fps and dropped frames; it is resent every few seconds, so members see the rate change. Receivers keep only known keys, with lengths and ranges limited, and an older member without `hw` shows as not shared. Captured fps counts frames the screen delivered; a dropped frame is one that the encoder pipe had not taken before the next arrived, so dropped frames with a healthy network point to a stalling sender.

Clocks: this PC's card shows its measured offset against true time ("8.2 s behind", In sync, or Unreachable), warning beyond 3 s and while unreachable; each member's card shows the ping estimate (`offset_us`, theirs minus ours). The Summary warns when the largest difference between members exceeds 3 s.

Two log lines only: a slow send (one write to a member took 1.5 s or more, with the number of sends queued for that member; at most once per member per 30 s) and the capture rate (once when the encoder falls behind the capture, again only after it recovered, and a line when a recording of at least 5 s ends with its average fps and dropped frames). Both are warnings, so the report's recent errors list them.

The report has `hardware`, `clocks` and `where data goes` sections, with relay hosts, names and addresses removed like the rest.

## Local API

A small HTTP server inside the app lets a person, an AI agent or another program read a room and do everything the window does except open windows. It is off by default and needs a token (Settings > API). [api.md](api.md) lists each endpoint; `src-tauri/src/ops.rs` is the one list of operations that the window and the API both dispatch into. The AI button (in every page header and the player header) opens a menu of three purposes (write notes from the transcript, summarize a recording into the game plan, find the mistakes in a match) and copies a plain-text prompt in the app's language with the API address, the token, the room and the recording; with the API off, the menu offers to turn it on.
