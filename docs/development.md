# Development

## Build

On Windows with Node.js, Rust (MSVC), the Visual Studio C++ Build Tools and an ffmpeg with NVENC, AMF, QSV and libx264 in PATH:

```
npm install
copy ffmpeg to src-tauri/binaries/ffmpeg-x86_64-pc-windows-msvc.exe
npm run build
```

The setup exe is in `src-tauri/target/release/bundle/nsis`. `scripts/build-installer.ps1` builds an offline installer that bundles that ffmpeg (a GPL build, so do not publish it) and writes its SHA-256 file.

## Release

Releases do not contain ffmpeg: the app downloads a pinned build into its data folder on first run and checks its SHA-256. To release, raise the version in `src-tauri/Cargo.toml` (`Cargo.lock` follows on the next build) and push to main. The `build` job builds the installer (on main only; other branches build the app alone), signed with the key in the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (unsigned, and not released, without them). When the tests and the end-to-end test pass on main and no release for that version exists, the `release` job in `.github/workflows/test.yml` publishes that tested installer with `latest.json`. Every run on main then copies that release's manifest to the `updater` release that the app reads: always as `latest-beta.json` (the Beta channel), and as `latest.json` (the Stable channel) only when the version has no pre-release part. So `0.9.1-1` reaches Beta only, and `0.9.1` reaches both. Use a numeric pre-release part, which every Windows installer format accepts. Keep the private key out of the repository; only the public key is in `tauri.conf.json`.

To run a second instance on one PC for testing, set `EZH_DIR` to a folder inside the app data folder (it holds that instance's identity key, recordings, log and WebView2 profile).

To try a change on another Windows PC over SSH without pushing: `scripts/deploy.sh <user@host>`. It sends the working tree, builds, and starts the app.

A deploy builds without an installer (`tauri build --no-bundle`); set `INSTALLER=1` to also build the installer, or `TEST=1` to only run the unit tests (`cargo test` in `src-tauri`). GitHub Actions runs the same tests on every push.

Start the app with `--api` or set `EZH_API=1` to turn the local API on at start. Set `EZH_API_PORT=<port>` to move the local API off its default port 47625 (the end-to-end test gives each instance its own). The API's unit tests are in `src-tauri/src/api.rs`, and `src-tauri/src/ops.rs` checks that every operation the page or the end-to-end test calls exists and is documented; `docs/llms.txt` is embedded in the app and drives the endpoint list in Settings (a test checks it against `docs/api.md`), so edit them together.

The hardware code is in `src-tauri/src/hw.rs` and the time check in `src-tauri/src/clock.rs`; their tests feed fake PowerShell output and made-up time answers, and `scripts/ui-test.mjs` covers the PCs and Where data goes rows and the shared live position with made-up data. In test mode `EZH_NTP=<host:port>` replaces the time server. `node --test scripts/ui-test.mjs` runs the UI's function tests (Markdown and game plan parsing, sidebar width, the plugins page, the capture buttons, the diagnostics rows), as GitHub Actions does.

The import and the folder export need ffmpeg: the app uses the one it downloaded, and the end-to-end test makes its tiny test videos with the ffmpeg in its folder. `docs/session-format.md` is the format; `src-tauri/src/session.rs` holds its parsers and their tests.

Set `EZH_RELAY_ONLY=1` to start an instance that uses only the relay, to test the slow path.

Set `EZH_TEST=<port>` for test mode: capture encodes a generated picture and two tones (ffmpeg `testsrc2` and `sine`) instead of the screen, app sound and microphone (a display source gives the test picture and a window source is never found, so it reads as closed), and the window's page accepts DevTools (CDP) connections on that local port.
